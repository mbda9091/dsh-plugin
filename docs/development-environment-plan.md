# 插件开发环境统一与隔离规划

> 状态：P0 脚本收尾已实现；P1–P4 仍为规划。更新日期：2026-10-30（Asia/Shanghai）。
> 建设顺序：**TS 脚本收尾与 PowerShell 兼容入口退场 → 统一环境配置 → 隔离开发宿主 → 插件包验收与正式安装。** P0 验证范围见[测试方案 §7.5](testing-plan.md#75-p0-脚本收尾2026-10-30)，本轮未引入开发 DSH 依赖或新环境数据布局。

## 1. 目标与边界

本仓库仍是插件开发仓库。开发时使用仓库管理的固定版本 DSH 作为隔离宿主；交付时只提供插件包，安装到用户指定的日常 DSH。开发宿主不替代用户 DSH，不进入插件 tarball，也不发布包含 DSH 本体的整套应用。

开发者只需选择一套普通 Node 24 和仓库指定的 pnpm。编译、仓库脚本、pnpm、自动化测试和开发用 DSH Web 尽量明确使用同一 `process.execPath`；不额外准备脚本专用、测试专用 Node。正式宿主保持自身的运行时约定，桌面 Electron 由应用管理。

目标流程：

```text
TS CLI 收尾
  → 统一工具与环境配置
  → 隔离开发 DSH：link 调试
  → 构建插件包：生成 .tgz
  → 干净测试环境：安装并验收该 .tgz
  → 用户指定 DSH/profile：安装同一份已验收 .tgz
```

本规划中的“隔离”是依赖、配置和数据隔离，不是限制插件访问操作系统的安全沙箱。桌面插件仍需相应平台/宿主的能力验收，不能凭 Web CI 成功推断 Electron、原生通知或真实重启已通过。

## 2. 已有基础与需要补齐的部分

当前业务脚本已迁入 `scripts/src/`，由 `bootstrap.mjs` 通过 tsc 编译后执行；P0 已移除 `.ps1`，同步帮助、文档与调用方，并增加直接运行 bootstrap 的回归测试。现有业务覆盖保留，验收平台边界见测试方案 §7.5。

已有 L4/L5 使用一次性 DSH home/profile、测试 patch 和 pnpm store，清除继承的 profile 目录/Web 地址，并在退出时清理服务。打包契约测试已覆盖 tarball 内容。这些是后续建设的基础，但当前仍共用 `tools.dshCli`，没有正式区分开发宿主与用户安装目标。

现有开发安装可以向日常 profile 写入 link，CI 从全局安装 DSH，pnpm 默认发现会扫描 DSH 私有运行时。后续需要改变这些选择规则；不能把已有测试隔离等同于整个日常开发流程已经隔离。

## 3. 三种环境的职责

| 环境 | DSH 来源 | 数据与配置 | 插件形态 | 生命周期 |
|---|---|---|---|---|
| 开发 | workspace 锁定的开发用 DSH | 仓库内专属 home/profile、开发 patch、store；不继承日常配置 | link | 持久，保留调试会话；显式重置 |
| 验收 | 同一锁定 DSH 版本；必要时增加明确的兼容版本矩阵 | 每次新建的 home/profile、测试 patch、store | 本次生成的 `.tgz` | 一次性，失败可保留现场 |
| 正式安装目标 | 用户选择的日常 DSH，通常来自其环境中的 CLI；桌面可显式指定 | 用户明确指定的 home/profile | 已验收的同一份 `.tgz` | 用户长期维护 |

开发与验收可以共享同一份只读 DSH 程序依赖，但不能共享可变 home/profile。所谓干净验收，不要求每次重新下载 DSH，要求从全新的配置与插件安装状态验证产物。

“装到环境 Node 里的 DSH”具体指向**环境中选定 DSH 的目标 profile 安装插件**，不是把插件复制进 Node 安装目录。正式安装不复制开发环境的配置、会话、凭据、profile manifest 或 DSH 本体。

## 4. 工具链与依赖归属

| 项目 | 规划中的管理方式 |
|---|---|
| Node | 普通 Node 24.x，由调用方选择；检查支持的主版本，记录完整版本与路径；不自动下载或切换另一套 Node |
| pnpm | 以根 `package.json.packageManager` 为准，当前 `11.28.5`；使用选定 pnpm 的脚本入口，由当前 Node 执行 |
| TS/esbuild/yaml/测试工具 | workspace 开发依赖与 lockfile 管理，通过冻结安装准备 |
| 开发 DSH | 根 workspace 精确版本 devDependency，当前计划基线 `@deepseek-ai/dsh@0.2.1-rc.2`；仅开发和验收使用 |
| DSH 类型与 Cordis | 与开发宿主接口基线对齐，当前 DSH 类型为 `0.2.1-rc.2`、Cordis 为 `4.0.5` |
| 正式 DSH | 用户独立管理；记录所选入口并检查兼容性，不由本仓库安装、升级、降级或覆盖 |
| 浏览器与系统工具 | L5 需要 Chrome 或匹配的 Playwright Chromium；当前 L2 需要系统 tar；按命令检查，避免让无关命令依赖它们 |

引入根开发依赖不改变插件自身零运行时依赖的目标。`pnpm pack` 的交付内容仍由各插件 `files` 控制，不含开发 DSH、Node、workspace `node_modules` 或本机配置。

Node 负责运行编译器，产物目标由编译选项决定。目前 tsc/esbuild 都使用 ES2022，不能据此保证宿主支持所有 Node API；还需在目标 DSH 运行时验证。开发 Node 与正式宿主不必是同一文件或精确小版本。

## 5. 配置边界与选择规则

后续配置应区分以下职责；这里只确定语义，具体字段名与 CLI 名称在实施时连同 schema、帮助和迁移步骤一起确定，不将示意名称当作当前可用接口。

| 配置职责 | 来源与规则 |
|---|---|
| 仓库工具 | 选定 Node 进程、pnpm 位置和仓库依赖版本；不再默认扫描 Codex/DSH 私有 Node/pnpm 目录 |
| 开发宿主 | 从 workspace 锁定依赖解析公开 CLI 入口；不从 PATH 或用户 `DSH_CLI` 回退到日常宿主 |
| 开发数据 | 仓库内专属目录、固定用途的 profile、开发 patch；可持久复用，但不得指向用户 home/profile |
| 测试数据 | harness 创建的新目录；外部覆盖不得把它指向现有日常或开发 home |
| 正式安装目标 | 具名绑定或显式参数指定的 DSH CLI、home、profile、surface/platform；仅安装/目标状态命令消费 |

正式目标允许从环境 PATH 发现候选，但必须排除本仓库 `node_modules/.bin` 和开发 DSH 的实际路径；npm/pnpm 启动脚本可能把本地 `.bin` 插到 PATH 前面，不能直接取第一个 `dsh`。发现结果应展示并固定为明确目标；没有明确目标时，正式安装停止，不能默认为用户 `desktop` 或回退到开发宿主。

开发/测试子进程清理继承的 `DSH_HOME`、`DSH_PROFILE`、`DSH_PROFILE_DIR`、`DSH_WEB_URL`、`DSH_CLI` 和 store 覆盖，再填入自己的上下文。只改子进程环境，不修改用户的系统环境变量、全局 npm 配置或全局 DSH 安装。

旧 `tools.dshCli` 同时承担开发和正式安装语义，不能在升级时盲目复制给两边。迁移时将其作为待核对的旧目标信息保留，开发入口重新从锁定依赖派生；home/profile 没有明确依据时不启用正式安装。新 schema 必须有显式迁移、预览和备份，不在日常运行时静默改写 v1 文件。现有 `DSH_CLI` / profile 环境变量的兼容映射也要在该阶段明确，不能继续无差别影响所有命令。

## 6. 隔离开发与验收

开发数据建议放在仓库内独立且被 Git 忽略的目录，例如 `.local/dsh-dev/`。该目录不能被常规 `.tmp` 清理顺带删除；其布局包含 home、store 和日志。创建前验证实际路径与 symlink/junction，禁止与用户数据或测试目录重叠。实施时先加忽略规则，再生成数据。

测试继续使用 `.tmp` 下每次新建的目录。开发/测试只读取自身 patch；HMR 监听范围明确限制到本仓库插件产物。开发可使用 link，测试不能仅凭 link 结果验收：应将真实 tarball 安装进干净 profile，检查安装结果为包内容而非源码 junction。

默认不读取、复制或自动导入日常凭据、会话及审批策略。需要真实模型调用的人工开发场景，在开发环境内由用户单独配置；自动化测试沿用不需要个人模型凭据的测试方式。使用独立端口、明确的本地监听地址和进程归属，退出只清理自己启动的进程。

桌面专属能力需另行验证桌面应用是否支持隔离 home、独立启动及单实例边界；能力未验证前，不宣称开发 Web 能完整替代桌面测试，也不能直接在日常桌面 profile 上运行自动化替代验收。

## 7. 插件包交付与正式安装

构建后生成 tarball，记录包名/版本、文件 SHA-256、源码状态标识、开发宿主版本、Node/工具链版本、targets 和验收结果。记录保存在忽略的本地报告目录，不自动发布或上传。

验收对象必须是将要安装的那一份文件。正式安装前校验哈希及包契约，不能在验收后自动重打包再安装；重新构建或文件变化会使旧验收记录失效。默认安装 tarball，日常宿主不使用开发 link。

正式安装的预览至少展示：目标 DSH 路径和版本、目标 home/profile、平台/场景、插件包路径/哈希及计划操作。安装前检查目标兼容性，范围不明确或版本未验证时给出差异，不自动替用户升级宿主。

实际通过该目标的插件管理机制安装，只修改指定 profile 的插件依赖与 bundle 记录；不复制开发 profile，不手改 profile manifest，不重装 DSH。沿用已存在的 add 覆盖和解析检查，避免 Windows 下 remove link 跟随 junction 删除源码的问题。安装结果记录 applied/warnings/加载状态，需要重启时明确报告，重启与能力验证按目标宿主规则处理。

## 8. 建设顺序与阶段出口

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| P0：TS 脚本收尾 | **已实现，Windows 验收通过**：Node/TS CLI 主入口、文档/帮助/测试/调用方已迁移，PS 入口已删除；证据见测试方案 §7.5 | 本轮 macOS 矩阵待验证；业务执行不依赖仓库 PS 文件。此阶段未引入新的开发 DSH 依赖或改造环境数据布局 |
| P1：环境配置统一 | 区分仓库工具、开发宿主与正式目标；引入锁定的开发 DSH；明确版本/入口解析及旧配置迁移 | 一套 Node/pnpm 可准备工具链；开发入口与正式目标绝不互相回退，现有配置可预览迁移 |
| P2：开发环境隔离 | 持久开发 home/profile/store/patch、link 调试、明确的启动/停止/重置生命周期；CI 使用相同开发宿主依赖 | 开发操作不改动日常 DSH；自动化仍使用独立新目录，故障和退出均可清理自身进程 |
| P3：产物验收 | pack → 干净 profile 安装 tarball → L4/L5 与包契约 → 验收记录 | 哈希对应的 tarball 通过验收，未依赖开发 link 或个人配置 |
| P4：正式安装衔接 | 环境中绑定目标 DSH/profile；预览、兼容性检查、安装已验收包与结果检查 | 指定目标收到同一 tarball，开发数据不随包迁入，用户宿主未被替换 |

P0 完成后才启动 P1/P2，不把环境隔离作为 TS 收尾的前置或同时扩展其范围。P3 复用现有测试能力，P4 复用现有安装逻辑，但需要在 P1 的目标模型上明确区分用途。这里的顺序是工程建设顺序；建成后的日常流程始终是开发 → 包验收 → 正式安装。

本机配置第三阶段的 repair/migrate 设计继续保留。其字段归属、备份及事务能力可以复用，但需基于 P1 确定的新配置结构落实；旧的单一 `tools.dshCli` 设计不能先固化成最终接口。P1 所需的最小迁移应与新 schema 一起交付，完整路径修复/模板升级能力不作为 P0 的前置。

## 9. 验收重点

- 全新开发环境只有一套 Node 和指定 pnpm，没有全局 DSH、Codex/DSH 私有 runtime 时，冻结安装后可以准备开发宿主及运行测试。
- 故意在 PATH、环境变量、旧本机配置中放入另一份 DSH，开发和测试仍只选择锁定宿主；正式安装不会误选 workspace `.bin`。
- 开发 home、测试 home、正式目标 home 的路径与实际文件系统位置均不重叠；在隔离 fixture 中比较模拟日常配置前后哈希，证明开发/测试不修改它。自动化不读取真实个人凭据来做断言。
- 测试 profile 从零开始，安装的包与最终交付 tarball 哈希一致；源码 link、漏打包文件、包被替换或验收后重打包都会被发现。
- 正式安装在一个单独准备的“模拟用户 DSH”中验证，只改指定 profile 的插件记录；缺目标、版本不兼容和场景不匹配均不写入。
- 中断、端口冲突、安装失败与重启要求有明确结果；清理不删除持久开发数据、用户 home 或源码 junction。
- Windows/macOS 分别运行；桌面能力、原生通知及真实重启仍按其独立验收边界报告。

## 10. 实施前需确定的接口细节

以下是 P1/P2 的实现设计任务，不阻塞先做 P0：新 schema 的字段与版本、旧配置迁移映射、开发目录最终名称、具名安装目标的绑定方式、Node CLI 子命令命名、验收记录格式，以及桌面隔离启动的支持范围。

这些细节不能改变已确定的边界：只有一套仓库 Node 工具链；开发用 DSH 被锁定并隔离；正式目标由用户明确选择；交付物仅为插件包；先完成 TS 脚本再建设环境统一与隔离。
