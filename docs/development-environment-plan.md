## 1. 结论摘要

- **要解决的问题**：开发、测试和正式安装仍共用 DSH 入口；本机变量、全局工具和日常 profile 可能影响开发结果及安装目的地。
- **采用的方案**：使用一套仓库 Node/pnpm、锁定的开发 DSH，分开管理持久开发环境、一次性验收环境和明确绑定的正式目标；交付同一份已验收 tarball。
- **本轮边界**：实现六步配置与环境建设，并同步交付 35 组独立环境测试场景；插件功能继续由适用的 L1–L5 提供证据。桌面隔离能力、原生通知和真实重启不能以 Web 结果代替。
- **当前进展**：M4 `f481036` Windows ISO/环境 all/完整功能回归提交后复验通过；开发数据仍留在 `.local/dsh-dev/`，测试数据进入独立 `.tmp`。环境和插件报告分开记录，CI 检查本次完整证据，见 §9.9。字段、命令与恢复见 [v2 协议](configuration-v2.md)。M5/M6 未实现。
- **下一步**：补齐当前实现的两平台 fast/real 与功能 CI 证据，再推进 M5；执行顺序与第 10 节一致。

### 4.1 总体设计与环境职责

本仓库仍是插件开发仓库。开发时使用仓库管理的固定版本 DSH 作为隔离宿主；交付时只提供插件包，安装到用户指定的日常 DSH。开发宿主不替代用户 DSH，不进入插件 tarball，也不发布包含 DSH 本体的整套应用。

开发者只需选择一套普通 Node 24 和仓库指定的 pnpm。编译、仓库脚本、pnpm、自动化测试和开发用 DSH Web 尽量明确使用同一 `process.execPath`；不额外准备脚本专用、测试专用 Node。正式宿主保持自身的运行时约定，桌面 Electron 由应用管理。

目标流程：

```text
TS CLI 收尾
  → 统一工具与环境配置
  → 隔离开发 DSH：link 调试
  → 构建插件包：生成 .tgz
  → 干净测试环境：安装并验收该 .tgz
  → 用户指定 DSH/profile：安装同一份已验收 .tgz
```

本规划中的“隔离”是依赖、配置和数据隔离，不是限制插件访问操作系统的安全沙箱。桌面插件仍需相应平台/宿主的能力验收，不能凭 Web CI 成功推断 Electron、原生通知或真实重启已通过。

| 环境 | DSH 来源 | 数据与配置 | 插件形态 | 生命周期 |
|---|---|---|---|---|
| 开发 | workspace 锁定的开发用 DSH | 仓库内专属 home/profile、开发 patch、store；不继承日常配置 | link | 持久，保留调试会话；显式重置 |
| 验收 | 同一锁定 DSH 版本；必要时增加明确的兼容版本矩阵 | 每次新建的 home/profile、测试 patch、store | 本次生成的 `.tgz` | 一次性，失败可保留现场 |
| 正式安装目标 | 用户选择的日常 DSH，通常来自其环境中的 CLI；桌面可显式指定 | 用户明确指定的 home/profile | 已验收的同一份 `.tgz` | 用户长期维护 |

开发与验收可以共享同一份只读 DSH 程序依赖，但不能共享可变 home/profile。所谓干净验收，不要求每次重新下载 DSH，要求从全新的配置与插件安装状态验证产物。

“装到环境 Node 里的 DSH”具体指向**环境中选定 DSH 的目标 profile 安装插件**，不是把插件复制进 Node 安装目录。正式安装不复制开发环境的配置、会话、凭据、profile manifest 或 DSH 本体。

### 4.2 工具链与依赖归属

| 项目 | 规划中的管理方式 |
|---|---|
| Node | 普通 Node 24.x，由调用方选择；检查支持的主版本，记录完整版本与路径；不自动下载或切换另一套 Node |
| pnpm | 以根 `package.json.packageManager` 为准，当前 `11.28.5`；使用选定 pnpm 的脚本入口，由当前 Node 执行 |
| TS/esbuild/yaml/测试工具 | workspace 开发依赖与 lockfile 管理，通过冻结安装准备 |
| 开发 DSH | 根 workspace 精确版本 devDependency，当前计划基线 `@deepseek-ai/dsh@0.2.1-rc.2`；仅开发和验收使用 |
| DSH 类型与 Cordis | 与开发宿主接口基线对齐，当前 DSH 类型为 `0.2.1-rc.2`、Cordis 为 `4.0.5` |
| 正式 DSH | 用户独立管理；记录所选入口并检查兼容性，不由本仓库安装、升级、降级或覆盖 |
| 浏览器与系统工具 | L5 需要 Chrome 或匹配的 Playwright Chromium；当前 L2 需要系统 tar；按命令检查，避免让无关命令依赖它们 |

引入根开发依赖不改变插件自身零运行时依赖的目标。`pnpm pack` 的交付内容仍由各插件 `files` 控制，不含开发 DSH、Node、workspace `node_modules` 或本机配置。

Node 负责运行编译器，产物目标由编译选项决定。目前 tsc/esbuild 都使用 ES2022，不能据此保证宿主支持所有 Node API；还需在目标 DSH 运行时验证。开发 Node 与正式宿主不必是同一文件或精确小版本。

### 4.3 接口、配置与选择规则

配置职责如下；M1 的具体字段和已实现命令以 [v2 协议](configuration-v2.md)为准，后续阶段接口仍在各阶段确定。

| 配置职责 | 来源与规则 |
|---|---|
| 仓库工具 | 选定 Node 进程、pnpm 位置和仓库依赖版本；不再默认扫描 Codex/DSH 私有 Node/pnpm 目录 |
| 开发宿主 | 从 workspace 锁定依赖解析公开 CLI 入口；不从 PATH 或用户 `DSH_CLI` 回退到日常宿主 |
| 开发数据 | 仓库内专属目录、固定用途的 profile、开发 patch；可持久复用，但不得指向用户 home/profile |
| 测试数据 | harness 创建的新目录；外部覆盖不得把它指向现有日常或开发 home |
| 正式安装目标 | 具名绑定或显式参数指定的 DSH CLI、home、profile、surface/platform；仅安装/目标状态命令消费 |

正式目标允许从环境 PATH 发现候选，但必须排除本仓库 `node_modules/.bin` 和开发 DSH 的实际路径；npm/pnpm 启动脚本可能把本地 `.bin` 插到 PATH 前面，不能直接取第一个 `dsh`。发现结果应展示并固定为明确目标；没有明确目标时，正式安装停止，不能默认为用户 `desktop` 或回退到开发宿主。

开发/测试子进程清理继承的 `DSH_HOME`、`DSH_PROFILE`、`DSH_PROFILE_DIR`、`DSH_WEB_URL`、`DSH_CLI` 和 store 覆盖，再填入自己的上下文。只改子进程环境，不修改用户的系统环境变量、全局 npm 配置或全局 DSH 安装。

旧 `tools.dshCli` 同时承担开发和正式安装语义，不能在升级时盲目复制给两边。迁移时将其作为待核对的旧目标信息保留，开发入口重新从锁定依赖派生；home/profile 没有明确依据时不启用正式安装。新 schema 必须有显式迁移、预览和备份，不在日常运行时静默改写 v1 文件。现有 `DSH_CLI` / profile 环境变量的兼容映射也要在该阶段明确，不能继续无差别影响所有命令。

### 4.4 隔离开发、生命周期与异常路径

开发数据建议放在仓库内独立且被 Git 忽略的目录，例如 `.local/dsh-dev/`。该目录不能被常规 `.tmp` 清理顺带删除；其布局包含 home、store 和日志。创建前验证实际路径与 symlink/junction，禁止与用户数据或测试目录重叠。实施时先加忽略规则，再生成数据。

测试继续使用 `.tmp` 下每次新建的目录。开发/测试只读取自身 patch；HMR 监听范围明确限制到本仓库插件产物。开发可使用 link，测试不能仅凭 link 结果验收：应将真实 tarball 安装进干净 profile，检查安装结果为包内容而非源码 junction。

默认不读取、复制或自动导入日常凭据、会话及审批策略。需要真实模型调用的人工开发场景，在开发环境内由用户单独配置；自动化测试沿用不需要个人模型凭据的测试方式。使用独立端口、明确的本地监听地址和进程归属，退出只清理自己启动的进程。

桌面专属能力需另行验证桌面应用是否支持隔离 home、独立启动及单实例边界；能力未验证前，不宣称开发 Web 能完整替代桌面测试，也不能直接在日常桌面 profile 上运行自动化替代验收。

<a id="7-插件包交付与正式安装"></a>

### 4.5 插件包交付与正式安装

构建后生成 tarball，记录包名/版本、文件 SHA-256、源码状态标识、开发宿主版本、Node/工具链版本、targets 和验收结果。记录保存在忽略的本地报告目录，不自动发布或上传。

验收对象必须是将要安装的那一份文件。正式安装前校验哈希及包契约，不能在验收后自动重打包再安装；重新构建或文件变化会使旧验收记录失效。默认安装 tarball，日常宿主不使用开发 link。

正式安装的预览至少展示：目标 DSH 路径和版本、目标 home/profile、平台/场景、插件包路径/哈希及计划操作。安装前检查目标兼容性，范围不明确或版本未验证时给出差异，不自动替用户升级宿主。

实际通过该目标的插件管理机制安装，只修改指定 profile 的插件依赖与 bundle 记录；不复制开发 profile，不手改 profile manifest，不重装 DSH。沿用已存在的 add 覆盖和解析检查，避免 Windows 下 remove link 跟随 junction 删除源码的问题。安装结果记录 applied/warnings/加载状态，需要重启时明确报告，重启与能力验证按目标宿主规则处理。

### 4.6 兼容、迁移与回退

- **兼容影响**：现有 `tools.dshCli`、安装默认 profile、`DSH_CLI` 等通用覆盖语义会拆分。先交付适用表和报错提示；不能让旧变量继续无差别影响所有命令。
- **迁移顺序**：M1 冻结旧 schema，定义新结构和纯迁移步骤，预览、备份、校验后写入；旧 CLI 仅保留为待核对信息。M2 接入锁定开发依赖，M3 创建新开发数据，不把个人 patch 和凭据复制进去。
- **配置回退**：普通失败按原始字节备份和哈希条件恢复；中断或恢复失败保留 pending，停止消费不一致配置。先核对第三方改动再人工恢复，不承诺多文件原子性；细节沿用[本机配置事务设计](local-configuration-design.md#146-备份写入与失败恢复)。
- **安装回退边界**：保留逐包结果，已安装包与失败包分开报告；不通过 remove 回滚 link，不自动降级用户宿主，不承诺多包安装原子性。
- **清理边界**：普通测试只清理自身临时资源；持久开发数据仅显式重置。没有目录或进程归属证据时停止并诊断，不能扩大到用户目录或源码。

<a id="91-测什么与-l1l5-如何分工"></a>

#### 4.7.1 测什么，与 L1–L5 如何分工

环境配置测试回答的是：**配置有没有读对、宿主有没有选错、数据有没有写错地方、失败后能不能恢复、交付的是不是验收过的文件。** 它从第 1 步开始建设，每一步必须同时交付对应测试，不留到第 6 步集中补测。

| 测试对象 | 主要断言 | 不代表什么 |
|---|---|---|
| 环境配置测试 | 配置迁移、命令分流、工具选择、目录与进程归属、产物与目标一致性 | 不代表插件业务、UI 或桌面通知已经正确 |
| 现有插件 L1–L5 | 插件逻辑、包契约、加载、Web UI 和真实交互 | 不代表所有环境污染、迁移中断和错误目标都已覆盖 |

两者复用 Node/TS、fixture、真实 Web 启停等基础能力，但独立选择用例和报告结果。已有 `local-config`、`command-context`、`harness-lifecycle` 等相关测试应逐项映射到下面编号，能复用的迁入或直接引用同一测试实现，不复制两套断言。不能仅因某个旧测试文件存在就认定整个场景完成。

<a id="92-测试入口隔离设施与证据"></a>

#### 4.7.2 测试入口、隔离设施与证据

**入口：M4 已实现 CFG/TOOL/DEV/ISO 的 fast/real/all；ART/TGT 待后续阶段交付。**

```text
node scripts/bootstrap.mjs test-env --suite fast
node scripts/bootstrap.mjs test-env --suite real --pnpm-script <pnpm包>/bin/pnpm.cjs
node scripts/bootstrap.mjs test-env --suite all --pnpm-script <pnpm包>/bin/pnpm.cjs
node scripts/bootstrap.mjs test-env --suite fast --only ISO-01,ISO-02
```

- `fast`：使用纯逻辑、临时文件、假 CLI、受控小型子进程；不启动真实 DSH、不要求浏览器、不构建插件、不联网。适合每次配置修改后运行。
- `real`：使用已安装的锁定 DSH/pnpm，在一次性目录验证真实解析、安装、启动与清理；所需 fixture 包由该套测试自己准备，不依赖上一次 `dist` 或个人 profile。涉及 `ART-06` 的 L5 时还需要声明的测试浏览器；其他环境场景不要求浏览器。工具不全时给出明确失败，不能静默切换假 CLI。依赖下载准备在测试之前完成，联网安装依赖的集成场景单列为有网络前提。
- `all`：两套均运行，汇总各自结果。每步加入该步用例，后续尚未实现的场景在文档里保留待办，不注册成返回成功的空测试。阶段验收对照用例清单检查缺项。

**实现布局：** `test/src/environment/` 存环境用例，按 `fast/`、`real/` 分组；共用 helper 放 `test/src/harness/`；`scripts/src/commands/test-env.ts` 负责选择、编译、执行和报告。采用单独的测试 tsconfig/编译输出（如 `test/.build-env/`，先加入忽略规则），只编译环境测试及必要 helper，避免因为旧测试 import 插件 `lib` 而迫使快速测试先构建所有插件。继续使用 `tsc` + `node:test`，不新增运行时转译器或另一套 Node 工具定位。

**入口不能依赖被测配置健康：** 在加载真实 `scripts/config/local.json` 前分发 `test-env`，测试在临时仓库副本内生成有效、旧版、损坏等配置；损坏的真实本机配置不得阻止快速测试运行。bootstrap 仍可编译脚本，其 `scripts/.build` 写入不算被测配置副作用；用例不能把这项例外扩大到备份、profile 或工具安装。

**每个用例的 fixture：** 独立创建临时仓库、模拟用户 home、开发 home、测试 home、store 和可记录调用的 fake CLI。模拟用户目录里放无敏感内容的配置/会话/凭据哨兵文件；以路径清单、文件字节 SHA-256 和链接目标快照比较前后状态。没有变化只能证明未修改；“未读取个人文件”另由文件读取边界的访问记录和受控配置来源证明，不能用哈希不变冒充未读取。测试不接触真实个人凭据。

**进程与故障注入：** 用 fake CLI 将收到的参数、选定环境字段、`process.execPath` 写到 fixture 日志，不输出整个环境；真实子进程的输出使用现有文件捕获 helper，不新增管道式 spawn。迁移的备份、替换和提交点通过可替换的文件操作边界注入失败，并增加一次真实子进程中断测试；路径测试使用真实 symlink/junction，进程测试验证实际存活和端口，不只检查 mock 调用次数。故障注入只用于测试代码，不提供生产环境的危险隐藏参数。

**报告与清理：** 报告写到 `.tmp/environment-tests/<run-id>/report.json`，汇总含源码标识、平台、Node/工具版本、用例编号、执行类型、pass/fail/skip、时长、断言证据位置及清理结果；失败保留日志/fixture，成功清理可变数据并保留报告，`--keep` 可保留成功现场。清理失败作为失败报告，不能吞掉；保留现场也必须停止自己的进程。日志脱敏，不自动上传本机文件、备份、启动认证 URL 或完整环境变量。

**共享运行结果：** 同一批次、同一产物哈希的真实 L4/L5 可以只执行一次，环境验收引用其完整结果，CI 插件功能汇总也引用该结果；不能拿上一次运行或不同包的报告凑齐证据。先让独立入口可单独运行，再接入统一 CI 编排，避免环境测试反过来调用整条 `ci` 形成递归。

| TGT-05 / fast + real | 原目标有 link/旧 tarball、残留 junction；执行 add 覆盖与重解析 | spec 与实际包内容一致；无 remove 调用，源码仍在；状态能识别“tarball spec 但仍指向源码” |
| TGT-06 / fast + real / 人工 | 多包第二包安装失败、warnings、加载失败、restart-required；桌面目标独立人工验证 | 精确记录部分成功和失败，不伪造回滚；安装/加载/能力验证分开；不自动重启日常宿主，未验证桌面能力明确留待验收 |

<a id="82-实施与验收边界"></a>

### 5.1 实施与验收边界

- **第 1 步同步修改读取器与命令路由。** 不能只换 schema、实际调用仍共用宿主。开发入口先建立独立解析契约，第 2 步接入锁定依赖；依赖未就绪时明确失败，不能临时回退到旧入口。新 schema 必需的最小迁移随第 1 步交付，完整路径 repair 和 Web 模板升级可后续补齐。
- **第 3 步先加忽略规则，再创建数据。** `.local/dsh-dev/` 作为计划采用的持久目录，普通 `.tmp` 清理不得触及它；创建、复用和重置均检查真实路径及目录归属。不得自动导入日常凭据、会话或审批策略。
- **第 4 步验证宿主与数据隔离，第 5 步验证交付产物。** 测试需直接消费指定 tarball，不能用 harness 内重新打包的另一份文件替代该产物的验收。开发与测试可共用只读程序依赖，但不能共用可变 home/profile/store。
- **第 6 步不自动重打包。** 安装前校验验收记录、文件哈希和包契约，随后安装同一份文件；目标发现与绑定不得把 workspace `.bin` 或开发 DSH 当作日常宿主。不自动升级、降级或替换用户 DSH。
- **每步同步帮助、schema/example、文档与相关测试。** 规则发生变化时同步更新 `AGENTS.md` 中的当前命令与配置约定；规划接口在实现前仍须标为待实现。记录实际通过的平台和验收范围，不提前将整阶段标为完成。
- **桌面能力保持独立验收。** 桌面隔离启动、单实例边界、原生通知和真实重启不由 Web CI 覆盖；未验证前，不使用日常桌面 profile 自动化替代验收，也不将其计入已通过范围。

<a id="83-第一步把工具开发环境安装目的地分开配置"></a>

### 5.2 第一步：把“工具、开发环境、安装目的地”分开配置

**解决什么问题：** 当前一个 `tools.dshCli` 被开发、测试、安装共用。即使路径有效，也无法据此判断“这是开发宿主”还是“这是日常安装目的地”。这一步让程序能表达并执行这种区别。

**具体怎么做（按顺序）：**

1. **列清配置归属。** schema 就是配置文件的格式规则。为仓库工具、开发偏好、测试偏好、正式安装目标分别列出字段、类型、必填条件、默认值与来源。Node 使用当前进程，开发 DSH 从锁定依赖推导，不把它们再保存为可随意覆盖的第二份路径。正式目标保存名字、CLI、home、profile、surface/platform；名字只是这组地址的标签，例如“日常桌面”。没有目标也应是一份合法的开发配置。
2. **写出命令选择表。** 构建/打包只取工具；开发 Web/link 安装取开发上下文；L4/L5 取测试上下文；正式安装/目标状态取选定目标。“上下文”是本次操作已经确定的工具、路径和环境变量集合，确定后向下传递，内部函数不再各自从全局环境重新猜测。
3. **逐项处理旧参数。** 为 `--dsh-cli`、`DSH_CLI`、`DSH_HOME`、`DSH_PROFILE`、`DSH_PROFILE_DIR`、`DSH_WEB_URL`、pnpm/browser 参数列出“哪些命令接受、优先级、旧用法如何报错”。开发/测试不能被日常 DSH 变量重定向；不适用的显式参数报错，不能接收后悄悄忽略。正式目标必须整体明确，不能从几个无关来源拼出意外目的地。维护命令读取磁盘原值，不把临时覆盖保存回配置。
4. **先形成迁移计划，再写文件。** 冻结旧 schema，交付新 schema、example 和明确的版本迁移函数。保留浏览器、超时等个人设置；旧 DSH 路径保存为待核对信息，不自动激活目标，不把旧个人 Web patch 搬进开发环境。遇到无法确定的字段，展示缺项。开发宿主未准备好时提示完成第二步，不能回退旧 CLI。
5. **交付最小的可靠写入流程。** `config migrate` 的预览只报告字段动作、缺项与备份位置；执行时重新校验输入，先备份，再替换并核验。复用[本机配置方案 §14.5–§14.7](local-configuration-design.md#145-修复计划与预览)的锁、哈希检查、pending 和恢复原则。首版只迁移所需 JSON/维护记录，不顺带实现个人 YAML 重写或完整 repair。备份失败不写；并发修改不覆盖；中断留下可核对的恢复记录并阻止继续消费不一致配置。
6. **同步改读取器和调用方，建立环境测试入口。** `init/check/migrate` 与业务命令使用相应的读取路径；迁移不能先被“只接受新版”的读取器挡住。新增 §4.7 的快速测试入口，入口本身不依赖待测试的本机配置。第 1 步先用假宿主测试命令分流，真实开发宿主由第 2 步接入。

**主要落点：** `scripts/config/`、`scripts/src/core/config.ts`、`command-context.ts`、`scripts/src/commands/config.ts`、`scripts/src/cli.ts` 及各命令调用处。新增迁移/事务逻辑放 `scripts/src/core/`；环境测试放 §4.7.2 指定目录。schema 新增语法时同步扩展现有校验器及测试，不能只改 JSON schema、让运行时漏校验。

**最终交付：** 新旧配置格式与字段归属表、命令/参数适用表、可运行的初始化/检查/迁移、预览和恢复说明、独立环境测试入口及 `CFG-*` 用例。用户可以在未绑定正式目标时准备开发；旧配置只能通过显式迁移进入新格式。

**本步测试与出口：** §4.7.3 的 `CFG-01`–`CFG-06` 在 Windows/macOS 通过；补齐读取器和 CLI 的现有回归测试。证明预览不改文件、迁移保留个人值、目标缺失不会触发安装、故障可诊断恢复。本步不宣称真实开发 DSH 已能启动。

<a id="84-第二步让仓库使用固定的开发-dsh-和同一套-nodepnpm"></a>

### 5.3 第二步：让仓库使用固定的开发 DSH 和同一套 Node/pnpm

**解决什么问题：** “机器上碰巧有一份 dsh/pnpm”不等于开发者和 CI 使用同一版本。要把开发宿主变成可复现的 workspace 依赖。

**具体怎么做（按顺序）：**

1. 根 `package.json` 加入精确版本的开发 DSH devDependency，正常安装生成 lockfile；保留插件零运行时依赖。先核实该版本包的公开 CLI 入口和安装行为，再实现解析，不依赖桌面 asar 或硬编码私有目录。
2. 从 workspace 依赖定位开发 CLI，检查实际安装版本与锁定声明一致。缺包、入口缺失或版本错误直接给出修复命令；不搜索 PATH 中的另一份 DSH 顶替。
3. Node 检查支持的主版本并记录完整版本/路径。pnpm 依据根 `packageManager` 选择和检查脚本入口，用当前 `process.execPath` 启动；停止默认扫描 Codex/DSH 私有 runtime。第一次冻结安装所需 pnpm 由调用方预先准备，仓库命令不自动下载或切换工具。
4. 编译器、pnpm、开发 DSH 的 Node 入口统一走当前进程路径。检查 DSH 内部调用 pnpm 的路径，复用现有 shim 保证一致。esbuild 等原生程序仍使用平台可执行文件；用户正式桌面宿主仍使用自身 Electron。
5. 做一份工具诊断输出：版本、实际入口、来源、哪些命令需要它。构建不因浏览器缺失失败，配置迁移不因 DSH/pnpm 路径失效而无法运行。诊断不转储整个进程环境。

**主要落点：** 根 `package.json`/lockfile，`core/config-tools.ts`、`dsh-cli.ts`、`pnpm.ts`、`command-context.ts`；`config check` 的工具诊断。真实锁定包冒烟测试从本步开始加入独立环境测试，完整流水线切换留到第 4 步。

**最终交付：** 锁定的开发 DSH、统一工具解析与版本检查、更新后的准备说明、可复现的工具诊断、`TOOL-*` 用例。

**本步测试与出口：** §4.7.4 的 `TOOL-01`–`TOOL-05` 在两平台通过。至少有一次从全新 checkout、未配置全局 DSH 的环境完成冻结安装，并以锁定 CLI 在一次性 home 中完成真实探测。fake CLI 的参数测试不能替代这次真实验证。

<a id="85-第三步建立长期使用可停止和重置的开发环境"></a>

### 5.4 第三步：建立长期使用、可停止和重置的开发环境

**解决什么问题：** 开发 link 和调试会话需要保留，但不能落进日常 DSH，也不能随着测试清理消失。

**具体怎么做（按顺序）：**

1. 先添加忽略规则，再建立 `.local/dsh-dev/` 下的 home、store、logs 和管理记录；开发 patch 放在该受管范围，版本化模板仍放源码目录。管理记录注明仓库真实根和环境用途，用于判断目录归属，不能仅凭目录名字就认定可以删除。
2. 创建与复用前检查绝对路径、已存在父目录的真实位置及 symlink/junction；开发、测试、正式目标不得相等或互为父子。尚未存在的路径也要检查最近存在的祖先，避免只做字符串前缀比较。
3. 通过锁定 DSH 的公开初始化方式创建开发 profile；只使用仓库开发模板，不复制日常 patch、凭据、会话或审批策略。模型配置由开发者在该环境内另行设置，自动化测试不需要个人模型凭据。
4. 将开发安装指向固定开发上下文，先构建再安装 link，验证 spec 和实际链接位置；HMR 监听明确的插件产物范围。旧命令若原本可向日常 profile 写 link，改为新开发语义并同步提示和帮助。
5. 实现启动、状态、停止：使用本地监听地址、明确端口和就绪超时；记录自身子进程与运行标识。重复启动要报告已有实例，端口被其他服务占用时失败，不能杀占用者。停止核对归属，不能只按 PID 或端口猜测；正常停止保留会话和开发配置。
6. 实现显式重置：先列出受管范围，再停止自身实例，重新验证路径与归属后清理。没有归属证据、存在未知外部链接或进程身份不明时停止并诊断。已核对归属的插件 link 只解除链接本身，不能递归跟随到源码；不使用 `pnpm remove` 清理链接依赖。

**主要落点：** `.gitignore`，`commands/web.ts`、`install.ts`、`status.ts` 和 CLI；把路径检查、环境创建、进程生命周期的共用逻辑放 `core/`，供后续测试环境复用，持久数据保留规则单独传入。

**最终交付：** 可重复使用的开发 Web 环境、link 调试、启动/停止/状态/重置接口和说明、`DEV-*` 用例。命令最终名称在本步帮助中确定，不能让示意命令看起来已可使用。

**本步测试与出口：** §4.7.5 的 `DEV-01`–`DEV-06` 在两平台通过；真实 Web 启动、停止、再次启动后数据仍在，重置只清理本次受管开发数据。测试在临时仓库副本中操作，不能拿开发者正在使用的 `.local/dsh-dev/` 做破坏性测试。

<a id="86-第四步让本机测试和-ci-使用同样的隔离规则"></a>

### 5.5 第四步：让本机测试和 CI 使用同样的隔离规则

**解决什么问题：** 日常开发隔离了，L4/L5 或 CI 若仍找全局 DSH、继承用户 home，结果仍不可复现。测试程序自身选对环境需要独立验证。

**具体怎么做（按顺序）：**

1. L4/L5 通过第 2 步的解析器取得锁定宿主，创建 `.tmp` 内全新 home/profile/store；采用测试专用 patch，不读取持久开发数据。对现有 `--home` 等覆盖参数继续执行“新目录且在受管范围内”的检查。
2. 用共用的环境构造逻辑移除继承的 DSH 与 store 覆盖，再写入测试上下文；处理 Windows 环境变量大小写。测试所用用户配置文件位置也显式控制，覆盖可能影响安装的 npm/pnpm 配置来源，不修改机器全局配置。保留运行所需的正常系统变量，不盲目清空整个环境。
3. 统一成功、失败、超时、中断的清理：退出自己的服务、关闭端口；成功默认清理可变测试数据，失败保留现场，`--keep` 保留成功现场。无论哪种结果都生成报告；报告生成失败不能被当作测试成功。
4. CI 去掉全局 DSH 安装，准备 Node 24 和指定 pnpm，冻结安装 workspace 依赖。添加独立的环境测试结果，再运行原有类型检查与 L1–L5；本地和 CI 调用同一套 Node CLI。
5. 每个环境测试进程使用独立 fixture 根目录和端口。Windows/macOS 均验证两次运行互不污染；真实并发场景用两个受控子进程验证，不依赖同进程修改全局变量来模拟。

**主要落点：** `core/web-harness.ts`、`commands/l4.ts`、`l5.ts`、`ci.ts`、测试 harness、`.github/workflows/tests.yml`。环境测试具备自己的汇总报告，CI 总报告只引用其结果，不把它混称为插件 L4/L5。

**最终交付：** 共用的隔离上下文、改造后的 L4/L5 和 CI、两平台独立环境测试报告、`ISO-*` 用例。

**本步测试与出口：** §4.7.6 的 `ISO-01`–`ISO-06` 与前面三步环境用例通过，原有类型检查和 L1–L5 仍通过。分别记录“环境隔离通过”和“插件功能回归通过”，任一失败都不能标为本步完成。

<a id="87-第五步验收具体的一份插件包并保留可核对的证据"></a>

### 5.6 第五步：验收具体的一份插件包，并保留可核对的证据

**解决什么问题：** 源码 link 能运行，不代表打出的包完整；测试时生成的包能运行，也不代表最后安装的是那一份。

**具体怎么做（按顺序）：**

1. 构建后打包，生成本次产物清单，记录每个 `.tgz` 的路径、包名/版本、SHA-256、targets、源码状态和构建批次。源码状态至少包含提交标识与未提交变更摘要，不能只写 commit 然后忽略工作区变化。
2. 让验收命令接收明确的产物清单；检查清单中所有包存在且哈希、包元数据一致后，在全新测试 profile 安装。L4/L5 的产物模式不得内部重打包，也不得从源码目录加载被测插件。
3. 验证实际安装路径与包内容。正常 pnpm store 链接不等于失败；要确认解析到本次包的内容、没有回到仓库源码 junction，且包不含 DSH 本体、本机配置和 workspace 依赖目录。
4. 调用现有包契约和适用的 L4/L5，记录每个包及 surface/platform 的结果。桌面专属包不能因为被 Web 测试跳过就成为“已验收”；需要的桌面证据缺失时标为未完成，阻止其进入对应正式安装。
5. 写验收记录：格式版本、产物清单/哈希、构建批次、源码状态、工具链/宿主版本、测试范围与用例结果、开始结束时间、失败或未覆盖项。建议将产物对应记录保存在 `dist/verification/` 并按批次组织，原始测试日志仍放 `.tmp`；清理测试现场不会误删唯一的交付凭据，重新 pack 不复用旧批次成功标记。
6. 安装前再次校验记录与文件。缺记录、缺必需结果、失败结果、包变化或当前交付批次被重建时拒绝使用旧验收；不能仅凭同名同版本或进程退出码为 0 判断通过。安装消费期间使用经过校验的固定文件并防止并发覆盖，检测到变化则终止该次交付。

**主要落点：** `commands/pack.ts`、新增产物验收命令与记录模块、L4/L5 的指定产物入口、安装前校验、包契约测试。验收记录只是本机流程证据，不作为防恶意篡改的签名系统。

**最终交付：** 产物清单、按指定包验收的入口、可检查的验收记录、失效规则、`ART-*` 用例。一份验收记录必须能回答“哪个文件，在什么环境下，通过了哪些检查”。

**本步测试与出口：** §4.7.7 的 `ART-01`–`ART-06` 通过；至少一份真实 Web 适用插件 tarball 走完清单 → 安装 → 功能验收 → 记录，安装哈希与记录一致。环境测试验证证据流转，插件功能结果仍由适用的 L4/L5 提供，两者不可互相代替。

<a id="88-第六步把已验收的包安装到明确选中的日常目标"></a>

### 5.7 第六步：把已验收的包安装到明确选中的日常目标

**解决什么问题：** 最后一步既要装对地方，也要装对文件，并能说明安装失败或需要重启时处于什么状态。

**具体怎么做（按顺序）：**

1. 实现正式目标的发现、绑定、查看和选择。发现只是列候选，排除 workspace `.bin` 和开发 DSH 的真实路径；只有用户明确给出的完整目标才持久保存。初次绑定和每次安装前都校验 CLI、home/profile、平台与场景，防止绑定后路径被换成 junction 或重叠目录。
2. 不再默认选择 `desktop`。具名目标或一组完整显式参数二选一；冲突组合报错。旧环境变量的兼容行为遵循第 1 步的适用表，不暗中补齐目的地。
3. 生成预览：目标入口/版本、home/profile、surface/platform、每份包的路径/哈希、验收范围、计划操作及不兼容项。对所选包整体预检；阻断项存在时不开始安装。支持按场景明确选择子集，不能把跳过的包报为已安装；现有 `--all` 等强制选项不得绕过正式交付门禁。
4. 将第 5 步通过校验的固定文件交给目标插件管理机制，沿用 add 覆盖和必要的重解析，不调用 remove、不手改 manifest。只在选定 profile 内安装；pnpm 必要的依赖、lockfile 和 bundle 更新属于该操作，不能借安装复制开发配置或改其他 profile。
5. 安装后分别检查依赖 spec、解析路径、包内容、bundle/行状态与 warnings。记录每包结果；部分包已成功而后续包失败时如实列出，不承诺多包安装原子回滚，不通过危险的 remove 尝试回滚。
6. 区分“文件已安装”“宿主已加载”“能力已验证”。需要重启时报告待重启，不自动重启日常应用，也不把加载未确认报为已生效。正式宿主版本没有相应验收依据时停止并说明缺少哪项证据，不自动升级用户宿主。

**主要落点：** 目标绑定命令、`commands/install.ts`、`status.ts`、目标解析和产物校验模块；替换旧 `stable-install` 的隐式目标语义，同步帮助与使用文档。

**最终交付：** 可管理的具名目标、只读安装预览、安装已验收包的入口、逐包结果报告、`TGT-*` 用例和桌面人工验证说明。自动化交付测试只使用隔离的模拟用户宿主。

**本步测试与出口：** §4.7.8 的 `TGT-01`–`TGT-06` 通过；在独立准备的真实普通 Node DSH 目标中完成一次交付，CLI 实际入口与开发 DSH 不同，home/store 也独立。桌面/Electron 的入口分流可自动测试，真实加载和重启仍需单列平台证据。
